# Session 14: Kubernetes Troubleshooting

## Overview

This session focuses on troubleshooting common Kubernetes problems using `kubectl` commands and a systematic debugging approach.

The main objectives are:

- Understand important Kubernetes troubleshooting commands.
- Identify common Pod and application failures.
- Investigate Kubernetes events and logs.
- Find the root cause of failures.
- Apply appropriate fixes.
- Verify that the issue has been resolved.
- Document the troubleshooting process.
- Complete a Kubernetes troubleshooting mini project.

---

# Task 1: Kubernetes Troubleshooting Commands

## 1. `kubectl get`

The `kubectl get` command is used to view the current state of Kubernetes resources.

### Get Pods

```bash
kubectl get pods
```

Example:

```text
NAME                         READY   STATUS    RESTARTS   AGE
yatri-app-7d8f6c9b8d-x2abc   1/1     Running   0          5m
yatri-app-7d8f6c9b8d-p4xyz   1/1     Running   0          5m
```

### Get all resources

```bash
kubectl get all
```

### Get Services

```bash
kubectl get services
```

### Get Deployments

```bash
kubectl get deployments
```

### Get Pods in all namespaces

```bash
kubectl get pods -A
```

This command is useful as the first step when investigating a Kubernetes problem.

---

# 2. `kubectl describe`

The `kubectl describe` command provides detailed information about a Kubernetes resource.

For a Pod:

```bash
kubectl describe pod <pod-name>
```

For a Deployment:

```bash
kubectl describe deployment <deployment-name>
```

For a Service:

```bash
kubectl describe service <service-name>
```

The most useful section during troubleshooting is usually:

```text
Events:
```

For example:

```text
Events:
  Type     Reason     Message
  ----     ------     -------
  Warning  Failed     Failed to pull image
  Warning  BackOff    Back-off pulling image
```

This can help identify the root cause of a problem.

---

# 3. `kubectl logs`

The `kubectl logs` command displays application logs generated by a container.

```bash
kubectl logs <pod-name>
```

For a specific container:

```bash
kubectl logs <pod-name> -c <container-name>
```

For the previous container instance:

```bash
kubectl logs <pod-name> --previous
```

This is particularly useful for investigating:

- Application crashes
- Configuration errors
- Database connection failures
- Startup errors
- Runtime exceptions

---

# 4. `kubectl exec`

`kubectl exec` allows commands to be executed inside a running container.

Example:

```bash
kubectl exec -it <pod-name> -- sh
```

Once inside the container:

```bash
ls
```

Check environment variables:

```bash
env
```

Test DNS:

```bash
nslookup kubernetes.default
```

Test network connectivity:

```bash
wget -qO- http://<service-name>
```

Exit the container:

```bash
exit
```

`kubectl exec` is extremely useful for investigating problems from inside the application environment.

---

# 5. `kubectl events`

Kubernetes events provide information about actions and failures occurring in the cluster.

Run:

```bash
kubectl events
```

Events can also be sorted:

```bash
kubectl events --sort-by=.lastTimestamp
```

For a particular namespace:

```bash
kubectl events -n default
```

Events can reveal problems such as:

- Failed image pulls
- Scheduling failures
- Container crashes
- Failed mounts
- Probe failures
- Insufficient resources

---

# 6. `kubectl explain`

`kubectl explain` provides documentation about Kubernetes API resources and fields.

For example:

```bash
kubectl explain pod
```

Explain a specific field:

```bash
kubectl explain pod.spec.containers
```

For Deployments:

```bash
kubectl explain deployment.spec
```

For Services:

```bash
kubectl explain service.spec
```

This is useful when you are unsure about the structure or purpose of a Kubernetes YAML field.

---

# 7. `kubectl top`

The `kubectl top` command displays resource utilization.

For Pods:

```bash
kubectl top pods
```

Example:

```text
NAME                         CPU(cores)   MEMORY(bytes)
yatri-app-7d8f6c9b8d-x2abc   25m          50Mi
yatri-app-7d8f6c9b8d-p4xyz   20m          48Mi
```

For nodes:

```bash
kubectl top nodes
```

This command is useful for identifying:

- High CPU usage
- High memory usage
- Resource pressure
- HPA-related problems

The command requires a functioning Metrics Server.

---

# 8. `kubectl get -o wide`

The `-o wide` option provides additional information.

```bash
kubectl get pods -o wide
```

Example:

```text
NAME                         READY   STATUS    IP           NODE
yatri-app-7d8f6c9b8d-x2abc   1/1     Running   10.244.1.5   worker-1
```

It can display:

- Pod IP
- Node
- Container information
- Additional resource details

This is particularly useful when troubleshooting networking and scheduling problems.

A systematic troubleshooting process is followed for every problem:

```text
Identify
   |
   v

   v
Find Root Cause
   |
   v
Fix
   |
   v
Verify
   |
   v
Document
```

# Issue 1: CrashLoopBackOff

## Problem

A Pod repeatedly starts and crashes.

Example:

```bash
kubectl get pods
```

Output:

```text
NAME          READY   STATUS             RESTARTS
broken-app    0/1     CrashLoopBackOff   5
```

## Step 1: Investigate

Check the Pod:

```bash
kubectl describe pod broken-app
```

Check logs:

```bash
kubectl logs broken-app
```

If the container has restarted:

```bash
kubectl logs broken-app --previous
```

## Possible Root Cause

The application may be terminating because of:

- Invalid configuration
- Missing environment variable
- Application exception
- Incorrect command
- Database connection failure
- Missing configuration file

Example log:

```text
ERROR: DATABASE_URL environment variable is missing
```

## Solution

Add the required environment variable:

```yaml
env:
  - name: DATABASE_URL
    value: "postgres://database:5432/app"
```

Apply:

```bash
kubectl apply -f deployment.yaml
```

## Verify

```bash
kubectl get pods
```

Expected:

```text
NAME          READY   STATUS    RESTARTS
broken-app    1/1     Running   0
```

# Issue 2: ImagePullBackOff

## Problem

The Pod cannot download its container image.

Example:

```text
NAME          READY   STATUS             RESTARTS
broken-app    0/1     ImagePullBackOff   0
```

## Investigation

Run:

```bash
kubectl describe pod broken-app
```

Look at the Events section.

Example:

```text
Failed to pull image "nginx:invalid"
```

## Root Cause

The image name or tag is incorrect.

For example:

```yaml
image: nginx:invalid
```

## Solution

Change it to a valid image:

```yaml
image: nginx:alpine
```

Apply:

```bash
kubectl apply -f deployment.yaml
```

## Verify

```bash
kubectl get pods
```

Expected:

```text
broken-app   1/1   Running
```

# Issue 3: ErrImagePull

## Problem

The Kubernetes node is unable to pull the requested container image.

Example:

```text
ErrImagePull
```

## Investigation

```bash
kubectl describe pod <pod-name>
```

Check:

```text
Events:
```

Possible errors:

```text
repository does not exist
manifest unknown
pull access denied
```

## Possible Causes

- Incorrect image name
- Incorrect image tag
- Private image without credentials
- Registry authentication failure
- Registry unavailable

## Solution

For a public image, correct the image name.

For a private image, configure an appropriate image pull secret.

Verify:

```bash
kubectl get pods
```

---

# Issue 4: Pending Pod

## Problem

A Pod remains in the `Pending` state.

Example:

```text
NAME          READY   STATUS
yatri-app     0/1     Pending
```

## Investigation

Run:

```bash
kubectl describe pod yatri-app
```

Check the Events section.

Possible output:

```text
0/2 nodes are available: insufficient cpu
```

## Root Cause

The cluster does not have enough resources to schedule the Pod.

Other possible causes include:

- Node selector mismatch
- Taints and tolerations
- Unavailable nodes
- PersistentVolume problems
- Affinity constraints

## Solution

Depending on the cause:

- Reduce resource requests.
- Add more cluster capacity.
- Correct node selectors.
- Configure appropriate tolerations.
- Fix storage configuration.

For example:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
```

## Verify

```bash
kubectl get pods
```

Expected:

```text
yatri-app   1/1   Running
```

---

# Issue 5: ContainerCreating

## Problem

A Pod remains in:

```text
ContainerCreating
```

for an unusually long time.

## Investigation

Run:

```bash
kubectl describe pod <pod-name>
```

Check the Events section.

Possible causes include:

- Volume mounting failure
- Image download
- CNI/networking issue
- Secret or ConfigMap mounting problem
- Storage attachment issue

## Root Cause Example

A referenced Secret does not exist.

Example:

```text
MountVolume.SetUp failed
secret "database-secret" not found
```

## Solution

Create the required Secret:

```bash
kubectl apply -f secret.yaml
```

Then verify:

```bash
kubectl get secret
kubectl get pods
```

---

# Issue 6: Service Connectivity Problems

## Problem

A Pod is running but another application cannot connect to its Service.

## Investigation

Check Services:

```bash
kubectl get services
```

Check endpoints:

```bash
kubectl get endpoints
```

If the Service has no endpoints:

```text
NAME          ENDPOINTS
yatri-service <none>
```

the Service is not finding the application Pods.

## Root Cause

The Service selector does not match the Pod labels.

For example, the Service has:

```yaml
selector:
  app: backend
```

while the Pod has:

```yaml
labels:
  app: yatri-backend
```

## Solution

Make the labels and selectors match.

Example:

```yaml
selector:
  app: yatri-backend
```

Apply:

```bash
kubectl apply -f service.yaml
```

## Verify

```bash
kubectl get endpoints yatri-service
```

Expected:

```text
NAME            ENDPOINTS
yatri-service   10.244.1.10:8080
```

# Issue 7: DNS Problems

## Problem

A Pod cannot resolve another Kubernetes Service by name.

## Investigation

Enter the Pod:

```bash
kubectl exec -it <pod-name> -- sh
```

Try:

```bash
nslookup kubernetes.default
```

Then test the application Service:

```bash
nslookup yatri-service
```

## Check CoreDNS

```bash
kubectl get pods -n kube-system
```

Look for CoreDNS:

```text
coredns-xxxxx
coredns-yyyyy
```

Check its logs:

```bash
kubectl logs -n kube-system deployment/coredns
```

## Possible Causes

- CoreDNS not running
- Incorrect Service name
- Incorrect namespace
- Network policy blocking DNS
- Cluster networking problems

## Solution

Verify the Service:

```bash
kubectl get service yatri-service
```

If the Service is in another namespace, use:

```text
yatri-service.namespace.svc.cluster.local
```

Verify CoreDNS:

```bash
kubectl get pods -n kube-system
```

# Issue 8: Pod Networking Problems

## Problem

Pods are running but cannot communicate with each other.

## Investigation

Get Pod IP addresses:

```bash
kubectl get pods -o wide
```

Example:

```text
NAME          IP            NODE
backend       10.244.1.10   worker-1
frontend      10.244.1.11   worker-1
```

Enter a Pod:

```bash
kubectl exec -it frontend -- sh
```

Test connectivity:

```bash
wget -qO- http://10.244.1.10:8080
```

## Possible Causes

- CNI plugin failure
- NetworkPolicy restrictions
- Incorrect Service configuration
- Incorrect ports
- Node networking issues

Check network-related Pods:

```bash
kubectl get pods -n kube-system
```

Check NetworkPolicies:

```bash
kubectl get networkpolicy
```

# Issue 9: Configuration Problems

## Problem

The application starts but does not behave correctly because of incorrect configuration.

Common configuration sources include:

- ConfigMaps
- Secrets
- Environment variables
- Volume-mounted configuration files

## Investigation

Check the Pod:

```bash
kubectl describe pod <pod-name>
```

Check environment variables:

```bash
kubectl exec <pod-name> -- env
```

Check ConfigMaps:

```bash
kubectl get configmap
kubectl describe configmap <configmap-name>
```

Check Secrets:

```bash
kubectl get secret
kubectl describe secret <secret-name>
```

## Root Cause Example

The application expects:

```text
DATABASE_HOST=postgres-service
```

but the configuration contains:

```text
DATABASE_HOST=postgres
```

## Solution

Correct the ConfigMap:

```yaml
data:
  DATABASE_HOST: "postgres-service"
```

Apply:

```bash
kubectl apply -f configmap.yaml
```

Restart the Deployment if required:

```bash
kubectl rollout restart deployment <deployment-name>
```

Verify:

```bash
kubectl exec <pod-name> -- env | grep DATABASE_HOST
```

            |                     |
            v                     v

# Conclusion

Session 14 provides a practical approach to troubleshooting Kubernetes applications.

Kubernetes applications can fail for many reasons, including incorrect container images, application crashes, insufficient resources, configuration errors, Service selector problems, DNS failures, and networking issues.

The most effective troubleshooting approach is to start with a high-level view using:

```bash
kubectl get
```

and then investigate further using:

```bash
kubectl describe
kubectl logs
kubectl events
kubectl exec
```

Resource usage can be examined with:

```bash
kubectl top
```

and networking information can be obtained using:

```bash
kubectl get pods -o wide
```

The troubleshooting process should always follow a structured approach:

```text
Identify the problem
        ↓
Investigate
        ↓
Find the root cause
        ↓
Apply the fix
        ↓
Verify
        ↓
Document the result
```

By completing this session, the ability to diagnose and resolve common Kubernetes problems is developed, providing an important foundation for working with Kubernetes in real-world DevOps environments.
